# 三角洲下机助手：预置游戏模板与安装包方案

状态：讨论稿，尚未实施

## 当前问题与证据

仓库已经有以下预置资源：

- `assets/profiles/delta.json`
- `assets/profiles/valorant.json`
- `assets/templates/delta/*`
- `assets/templates/valorant/*`

普通打包配置 `Delta-Exit-Assistant.spec` 使用 `datas=[('assets', 'assets')]`，理论上会把这些资源带入 PyInstaller 包。

但 `Delta-Exit-Assistant-OneClick.spec` 使用 `datas=[]`。使用这个 spec 打包时，预置 profile、模板和图标资源不会被带入，因而用户看不到三角洲/瓦罗兰特的完整预设。它是当前“需要用户自己在 assets 中建立模板”的首要可疑原因。

## 资源分为两类

### 随程序发布的只读资源

- 内置游戏 profile
- 内置结算模板
- 程序图标和其他默认资源

它们应随安装包或 EXE 发布，由程序从打包资源目录读取，不要求用户手动创建 `assets`。

### 用户运行时数据

- `config.json`
- 用户新增的游戏 profile
- 用户重新抓取的模板
- 自定义提示音
- ROI 覆盖和用户偏好

这些数据不应写入 PyInstaller 的临时解包目录，也不应依赖 `Program Files` 的写权限。

## 推荐的资源策略

保留“内置默认资源 + 用户覆盖”的两层结构：

1. 安装目录或 PyInstaller 资源目录存放内置 profile 和模板，只读。
2. 用户数据放到 `%LOCALAPPDATA%\\DeltaExitAssistant`，作为唯一可写数据目录。
3. 用户目录中的同名 profile、模板或设置优先于内置版本，但缺失时自动回退到内置版本。
4. 首次运行时不要求用户创建任何目录；只有用户新增或修改内容时才创建用户数据目录。

这样既能让预置游戏开箱即用，也不会因为安装到受保护目录而无法保存设置。

## 单文件 EXE 与安装包

### 单文件 EXE

优点：下载和分发简单，不需要安装。

缺点：

- 每次启动都要解包到临时目录，资源路径和杀毒软件误报更难排查。
- 运行时修改不能写回 `_MEIPASS`，用户数据必须另放。
- 一个错误的 spec（例如 `datas=[]`）就会悄悄缺失全部预置资源。
- 用户容易把 EXE 放到只读目录，导致当前“写 EXE 同级”策略失败。

### 安装包 + onedir 程序目录

优点：

- 安装后的资源目录明确，profile 和模板随程序一起存在。
- 启动和资源加载更稳定，问题更容易诊断。
- 可以创建开始菜单/桌面快捷方式，并支持卸载和版本升级。

缺点：

- 发布物不再是单个文件。
- 需要处理安装、升级、卸载，以及用户数据保留策略。
- 安装目录仍可能是只读的，所以用户数据路径仍需独立设计。

## 推荐路线

先修正资源打包和运行时数据路径，再决定是否增加安装包：

1. 统一使用包含 `assets` 的主 spec，废弃或修正 `OneClick.spec` 的 `datas=[]`。
2. 增加启动自检：显示当前内置 profile/template 是否载入，并在缺失时给出明确错误，而不是静默地进入无模板状态。
3. 把配置、用户模板、用户 profile 和提示音迁移到 `%LOCALAPPDATA%\\DeltaExitAssistant`，保留旧版 EXE 同级数据的一次性迁移兼容。
4. 先发布 PyInstaller `onedir` 目录作为技术上最稳的测试包。
5. 用户体验稳定后，再用 Inno Setup 或 NSIS 将 `onedir` 目录包装成安装程序。
6. 如果仍需免安装版本，可另外提供单文件 EXE，但它应与安装版共用同一套资源查找和用户数据规则。

## 验收条件

- 全新机器上直接启动，不手动创建 `assets` 也能看到三角洲和瓦罗兰特。
- 两个预置游戏都能加载至少一个有效模板，并能完成一次检测。
- 安装到 `Program Files` 后，设置、ROI、模板和提示音仍能保存。
- 卸载程序时默认保留用户数据，升级时不覆盖用户自定义模板。
- 缺失资源时显示可理解的中文提示和资源路径，而不是无提示地“不运行”。
